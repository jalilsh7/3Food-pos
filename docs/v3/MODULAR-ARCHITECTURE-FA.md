# معماری ماژولار POS V3

## هدف

ساختار پروژه باید امکان عیب‌یابی مستقل، توسعه مرحله‌ای، ارتقای کنترل‌شده و تعویض زیرساخت هر قابلیت را فراهم کند؛ بدون اینکه تغییر یک قابلیت باعث درگیری غیرضروری سایر قسمت‌ها شود.

## قرارداد هر ماژول

هر قابلیت تجاری جدید در مسیر `src/modules/<id>/` قرار می‌گیرد و در حد نیاز این بخش‌ها را دارد:

- `manifest.ts`: شناسه پایدار، نسخه ماژول، وضعیت و قابلیت‌ها.
- `index.ts`: API عمومی و تنها مسیر مجاز import برای سایر ماژول‌ها.
- `domain/`: انواع، قواعد و توابع خالص کسب‌وکار؛ بدون وابستگی به React یا شبکه.
- `application/`: سناریوهای کاربردی و هماهنگی عملیات.
- `ui/`: صفحات و اجزای رابط کاربری.
- `infrastructure/`: اتصال به PHP API، دیتابیس و سرویس‌دهنده‌ها.
- `observability/`: رخدادها و ابزارهای عیب‌یابی با حذف اطلاعات محرمانه.
- `tests/`: آزمون‌های واحد و قرارداد ماژول.
- `migrations/`: فقط در صورت نیاز به تغییر ساختار داده و با نسخه‌بندی سازگار.
- `README.md`: مسئولیت‌ها، وابستگی‌ها، نقاط عیب‌یابی و روش توسعه.

همه پوشه‌ها از روز اول اجباری نیستند؛ وقتی نیاز واقعی ایجاد شد اضافه می‌شوند تا ساختار تشریفاتی و پیچیده نشود.

## قوانین وابستگی

1. ارتباط بین ماژول‌ها فقط از طریق `index.ts` یا قراردادهای مشترک مشخص انجام می‌شود.
2. وابستگی چرخه‌ای ممنوع است؛ ماژول‌ها نباید فایل‌های داخلی یکدیگر را import کنند.
3. Domain مستقل از UI، PHP، دیتابیس و provider می‌ماند.
4. منطق تجاری در صفحه React یا فایل راه‌انداز اصلی انباشته نمی‌شود.
5. اتصال‌های بیرونی پشت adapter قرار می‌گیرند تا تعویض ارائه‌دهنده بدون بازنویسی منطق ممکن باشد.
6. خطاها باید دارای شناسه ماژول، عملیات، زمان و سطح شدت باشند؛ رمز، کلید API، شماره کامل حساس و هدر احراز هویت نباید وارد لاگ شوند.
7. تغییر قرارداد ذخیره‌سازی یا API باید نسخه‌بندی، سازگاری با داده‌های قبلی و مسیر rollback داشته باشد.
8. ماژول‌ها باید تست مستقل و تست یکپارچگی مرزهایشان داشته باشند.

## راهبرد عیب‌یابی

سطوح استاندارد: `debug`, `info`, `warning`, `error`, `critical`. هر گزارش باید context ساختاریافته داشته باشد: `module`, `action`, `correlationId`, `timestamp`, `code`. اطلاعات محرمانه و متن کامل اعتبارنامه‌ها ممنوع است. خطاهای frontend و PHP باید با شناسه پیگیری قابل تطبیق باشند.

## راهبرد ارتقا

- نسخه ماژول و نسخه schema از هم مستقل نگهداری شوند.
- migrationها افزایشی و نسخه‌دار باشند؛ حذف ستون/داده در همان مرحله تغییر ناسازگار انجام نشود.
- تنظیمات جدید default امن داشته باشند و برای مشتریان قبلی قابل خواندن بمانند.
- feature flag برای قابلیت‌های تجاری و rollout مرحله‌ای استفاده شود.
- هر انتشار باید یادداشت تغییرات، پیش‌نیاز migration، روش backup و rollback داشته باشد.

## اجرای آزمایشی: پیامک

ماژول پیامک نخستین نمونه عملی است: `src/modules/sms/`. صفحه بدون تغییر رفتار به `ui/` منتقل شده، metadata رویدادها و parser متغیرها در `domain/events.ts` قرار گرفته و `index.ts` سطح عمومی را ارائه می‌دهد. فایل قدیمی POS صرفاً adapter سازگاری است. انتقال orchestration ارسال از `app.tsx` به لایه application و انتقال provider boundary به infrastructure در گام بعدی انجام می‌شود.

## ترتیب مهاجرت سایر قابلیت‌ها

1. پیامک (pilot) و تثبیت قراردادها.
2. مشتریان، باشگاه و کمپین‌ها.
3. سفارش و گردش وضعیت.
4. انبار و مواد اولیه.
5. فروش و صندوق.
6. گزارش، هزینه و تأمین‌کنندگان.
7. تنظیمات، کاربران و مجوزها.

مهاجرت هر بخش باید تدریجی باشد؛ ابتدا مرز و API مشخص، سپس انتقال منطق، سپس تست و در پایان حذف adapter قدیمی. بازنویسی یک‌باره کل POS مجاز نیست.
