# انتقال ماژول پیامک V2 به خط توسعه POS V3

تاریخ ثبت: 2026-11-25

## مبنا و مقصد

- مخزن: `jalilsh7/3Food-pos`
- سورس مرجع V2: شاخه `main`، commit `6ee3a9bdc5769753674b302e5afb081ab9390b5a`
- مقصد توسعه: شاخه `feature/3food-pos-next-release-v2`
- commit انتقال: `2048a7cb23140baf4554a33f0bb9fde72294a774`
- V2 و شاخه `main` در این انتقال تغییر نکرده‌اند.

## آنچه منتقل شد

1. صفحه کامل پیامک از V2 جایگزین صفحه قدیمی مقصد شد؛ شامل مدیریت الگوهای سفارش، متغیرهای مرتب‌شده، پیامک دستی/کمپین، فیلتر مخاطبان با AND/OR، شرط رضایت پیامکی و پیشرفت ارسال.
2. پشتیبانی از رویداد `order_dispatched` به مدل رویدادهای پیامک و صفحه الگوها اضافه شد.
3. تنظیم ارسال مستقل پیامک هر رویداد برای مدیر با فیلد `managerEnabled` منتقل شد.
4. شماره مدیر با `smsManagerPhone` به تنظیمات فروشگاه و مقدار اولیه store اضافه شد.
5. منطق ارسال رویدادها در برنامه به‌روزرسانی شد تا پیامک مشتری و مدیر مستقل باشند و ارسال مدیر در صورت فعال بودن تنظیم مربوط انجام شود.
6. فراخوانی پیامک برای وضعیت «ارسال شد» به گردش تغییر وضعیت سفارش اضافه شد.
7. اعتبارسنجی سمت سرور نیز `order_dispatched` را در فهرست رویدادهای نیازمند الگوی خدماتی قرار می‌دهد؛ بنابراین این رویداد نمی‌تواند ناخواسته از مسیر متن آزاد عبور کند.

## اجزایی که از قبل در مقصد وجود داشتند و حفظ شدند

- مسیرهای API تنظیمات، تشخیص خطا، ارسال، و همگام‌سازی صندوق پیامک.
- ذخیره اعتبارنامه ملی‌پیامک در MySQL با رمزگذاری AES-256-GCM و عدم بازگرداندن API Key به مرورگر.
- ارسال عادی از خط اختصاصی و ارسال خدماتی از مسیر `BaseServiceNumber`.
- ثبت گزارش ارسال در سمت سرور و رابط.
- صفحه تنظیمات اتصال ملی‌پیامک و گزارش عیب‌یابی؛ این قسمت با V2 هم‌راستا بود و بدون جایگزینی کامل فایل تنظیمات حفظ شد.

## مواردی که هنوز انجام نشده‌اند

- اجرای typecheck، lint، تست‌های PHP/API و build روی همین commit.
- آزمایش واقعی ارسال عادی و خدماتی روی هاست staging با اعتبارنامه مشتری.
- بررسی تحویل واقعی پیامک و تطبیق پاسخ‌های provider در سناریوهای موفق/ناموفق.
- تبدیل ارسال کمپین تک‌به‌تک فعلی به صف پایدار سمت سرور، همراه با retry کنترل‌شده و گزارش وضعیت تحویل؛ این قابلیت هنوز بخشی از انتقال حاضر نیست.
- بازبینی رضایت پیامکی در سطح ثبت و تاریخچه رضایت؛ فیلتر فعلی فقط مقدار `smsConsent === true` را رعایت می‌کند.

## نکات ادامه کار

- API Key و سایر اعتبارنامه‌ها نباید به frontend، رکورد عمومی تنظیمات یا فایل‌های قابل انتشار منتقل شوند.
- پیامک وضعیت سفارش باید فقط از الگوی خدماتی تأییدشده استفاده کند.
- کمپین و پیامک دستی باید از خط اختصاصی عادی استفاده کنند.
- هیچ ارسال واقعی در این انتقال اجرا نشده است؛ تأیید کد به معنی تأیید تحویل پیامک نیست.
- تغییرات این مرحله روی شاخه توسعه انجام شده و هیچ فایل هاست یا دیتابیس عملیاتی تغییر نکرده است.
