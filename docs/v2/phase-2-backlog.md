## یافته‌های قطعی فعلی در کد PHP

1. endpoint سفارش `totals` را از درخواست دریافت و همان را ذخیره می‌کند؛ فعلاً فقط subtotal را با قیمت محصول/گزینه‌ها مقایسه می‌کند. تخفیف، مالیات، امتیاز و total نهایی سمت سرور محاسبه نمی‌شوند.
2. endpoint ثبت سفارش idempotency key ندارد؛ تکرار درخواست می‌تواند سفارش تکراری بسازد.
3. endpoint bootstrap سفارش‌ها را با `LIMIT 500` برمی‌گرداند؛ تاریخچه کامل تضمین نمی‌شود.
4. endpoint تغییر وضعیت سفارش وجود دارد، اما endpoint ویرایش محتوای سفارش برای مدیر هنوز وجود ندارد.
5. store اصلی همچنان از Zustand `persist` استفاده می‌کند و کلاینت فعلی app-data در مسیر TanStack Start/Grok است؛ اتصال مستقیم به PHP API انجام نشده است.
6. محیط آزمون فعلی PHP 8.4 دارد اما فقط PDO پایه در فهرست افزونه‌ها دیده شد؛ `pdo_mysql` و MySQL واقعی در این محیط در دسترس/قابل تأیید نیستند.
7. `php -l php-backend/public/api/index.php` موفق بود؛ این فقط بررسی syntax است و صحت اجرای API یا SQL را اثبات نمی‌کند.

## معیار خروج از staging

هیچ deploy به دامنه اصلی تا زمانی انجام نشود که همه تست‌های خودکار و دستی بالا روی staging با MySQL واقعی موفق باشند، backup قابل بازیابی باشد، و چند دستگاه بدون سفارش تکراری یا از دست رفتن داده کار کنند.



## گزارش اجرای مجدد تست‌ها — 2026-11-17

### نتیجه قطعی روی آرشیو کاری محلی

- پس از بازیابی فایل‌های آزمون موردنیاز از سورس اصلی (فقط `.grok/skills/og` و `.grok/app-env.json` فاقد secret)، کل مجموعه تست‌های اسکریپتی با دستور `node --test 'scripts/**/*.test.mjs'` اجرا شد: **197 موفق، صفر ناموفق**.
- `php -l php-backend/public/api/index.php`: موفق.
- `php -l php-backend/private/config.example.php`: موفق.
- اجرای کامل `npm test` همچنان به علت نصب نبودن وابستگی‌های پروژه کامل نیست: 197 تست اسکریپتی موفق شدند، اما دو فایل تست TypeScript به علت نبود `@tanstack/react-start` و `jose` اجرا نشدند.
- تلاش برای `npm ci --ignore-scripts --no-audit --no-fund` در محیط فعلی به timeout رسید و `node_modules` ساخته نشد.
- `pdo_mysql` همچنان در PHP محیط اجرا وجود ندارد؛ تست MySQL واقعی ممکن نیست.

### وضعیت انتقال

این نتایج مربوط به آرشیو کاری محلی هستند. هنوز کل درخت سورس و backend به شاخه GitHub منتقل نشده‌اند؛ هیچ ادعایی مبنی بر انتقال کامل یا آماده بودن deploy وجود ندارد.


## وضعیت فعلی شاخه فعال — بازبینی سورس در 2026-11-23

شاخه مرجع: `feature/3food-pos-next-release-v2` در مخزن `jalilsh7/3Food-pos`.

### مواردی که در سورس فعلی پیاده‌سازی شده‌اند (بدون ادعای تست اجرا)
- سورس React/Vite و backend PHP/MySQL در همین شاخه موجود است؛ رابط با PHP session و bootstrap مرکزی کار می‌کند و Zustand دیگر داده عملیاتی را در localStorage persist نمی‌کند.
- احراز هویت username/password و کنترل نقش در API سمت PHP وجود دارد.
- قیمت محصول/افزودنی، تخفیف، مالیات، امتیاز و مبلغ سفارش در PHP اعتبارسنجی می‌شوند؛ ثبت سفارش، کسر موجودی، اثرهای وفاداری، redemption کد تخفیف و audit در تراکنش انجام می‌شود.
- idempotency سفارش و پرداخت کارتخوان وجود دارد؛ retry مبهم کلید قبلی را حفظ می‌کند و پاسخ قطعی رد سفارش اجازه کلید جدید می‌دهد.
- ویرایش سفارش مدیر و بازگردانی اثرهای موجودی/امتیاز، تغییر وضعیت سفارش و قواعد لغو پرداخت انجام می‌شود.
- بهای تمام‌شده recipe پس از قفل مواد اولیه و در همان تراکنش سفارش snapshot می‌شود.
- گزارش خلاصه از endpoint سمت سرور و بر اساس بازه تاریخ محاسبه می‌شود؛ گزارش‌های روزانه/ماهانه، سود و زیان، مالیات، تخفیف، روش پرداخت، مصرف مواد و مشتریان از API تغذیه می‌شوند.
- مدیریت مشتری، تخفیف، هزینه، تأمین‌کننده، پیامک، کاربران، تنظیمات، انبار و سایدبار در ماژول‌های جداگانه موجود است.
- اسکریپت بسته‌بندی cPanel اکنون bootstrap و تمام routeهای خصوصی PHP را کپی و در فهرست الزامات بسته کنترل می‌کند.

### موارد باز و نیازمند تکمیل/تصمیم/محیط بیرونی
- pagination/cursor برای bootstrap سفارش‌ها و گزارش‌های بزرگ هنوز باید از نظر مقیاس‌پذیری طراحی شود؛ bootstrap فعلی کل تاریخچه سفارش را برمی‌گرداند.
- صف پایدار عملیات آفلاین/همگام‌سازی چند دستگاه به‌صورت کامل پیاده‌سازی نشده؛ idempotency فقط از تکرار درخواست سفارش/پرداخت در retry جلوگیری می‌کند و جایگزین صف آفلاین نیست.
- فایل‌های شش وزن IRANYekanWeb FarsiNum در Git شاخه موجود نیستند؛ روی cPanel قبلی در `public_html/fonts/` قرار دارند و باید هنگام آپدیت حفظ شوند. فایل `iranyekanwebmediumfanum.woff` قبلاً خطای بارگذاری داده است و نیاز به بررسی روی هاست دارد.
- عامل ویندوز کارتخوان موجود است، اما هیچ درایور بانکی واقعی و تأییدشده در مخزن وجود ندارد؛ نتیجه تراکنش بدون درایور معتبر نباید موفق تلقی شود.
- پیامک واقعی به credential معتبر پنل و پذیرش روی هاست نیاز دارد؛ بکاپ/بازیابی و استقرار cPanel نیز باید در staging واقعی بررسی شوند.
- ZIP جدید نهایی هنوز ساخته نشده؛ ZIP اصلی `3food-pos-php-migration(1).zip` نباید overwrite شود.
- طبق دستور صریح مالک، هیچ تست، build، lint، typecheck یا آزمون دستی اجرا نکنید. وضعیت سورس فقط با مطالعه و بازخوانی فایل‌ها بررسی می‌شود. این محدودیت تا زمانی معتبر است که مالک صریحاً آن را تغییر دهد.
