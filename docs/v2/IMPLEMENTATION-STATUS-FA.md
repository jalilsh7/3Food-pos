# وضعیت مهاجرت 3Food POS به PHP/MySQL

تاریخ: 2026-11-18

## انجام‌شده در این مرحله
- محاسبه محلی رسید پس از ثبت سفارش اکنون همان کلید فعال/غیرفعال مالیات مرکزی را دریافت می‌کند؛ حالت مالیات خاموش دیگر بین مبلغ سرور و رسید چاپی محلی اختلاف ایجاد نمی‌کند.
- بازیابی پشتیبان محلی که فقط Zustand را تغییر می‌داد حذف شد؛ خروجی JSON باقی است اما restore واقعی تا پیاده‌سازی مسیر امن و تراکنشی MySQL غیرفعال است.
- فایل ZIP اصلی بدون تغییر حفظ شد و توسعه روی کپی کاری انجام شد.
- ممیزی وابستگی‌های محیط Grok/Vercel/Node و وضعیت ذخیره‌سازی مرورگر انجام شد.
- API پایه PHP برای راه‌اندازی مدیر، ورود/خروج، نشست امن، تغییر رمز، CSRF، محدودسازی تلاش ورود، RBAC و مدیریت کاربران موجود است.
- schema مرکزی MySQL برای کاربران، audit، داده‌های عمومی POS، شمارنده ترتیبی سفارش و سفارش‌ها اضافه شد.
- API دریافت bootstrap، ذخیره/خواندن/حذف رکوردهای منابع POS، ثبت سفارش با شمارنده قفل‌شده در transaction و تغییر وضعیت سفارش اضافه شد.
- ثبت سفارش، قیمت پایه و قیمت optionها را با داده محصول ذخیره‌شده در سرور تطبیق می‌دهد.
- ثبت سفارش از UI صندوق به PHP/MySQL متصل شد؛ UUID idempotency برای retry استفاده می‌شود و شناسه/شماره سفارش از سرور دریافت می‌شود.
- تغییر وضعیت سفارش‌های سروری ابتدا در PHP/MySQL ثبت و سپس در Zustand اعمال می‌شود؛ کنترل‌های UI نیز بر اساس نقش و گردش مجاز وضعیت محدود شدند.
- تغییرات دسته‌بندی، محصول، مواد اولیه و موجودی، مشتری، کد تخفیف، هزینه، قالب پیامک و تنظیمات فروشگاه از UI به API رکوردهای PHP متصل شدند؛ در خطای API تغییر محلی این عملیات اعمال نمی‌شود (قالب‌ها و تنظیمات متنی پس از خروج از فیلد ذخیره می‌شوند).
- ثبت سفارش در API دارای idempotency key است؛ retry با همان UUID و همان payload سفارش تکراری نمی‌سازد و استفاده مجدد از کلید با payload متفاوت رد می‌شود. migration شماره 003 و تغییر schema اضافه شد.
- در رابط مدیر، انتقال یک‌باره داده‌های اصلی دستگاه به دیتابیس خالی اضافه شد؛ انتقال شامل منو، مواد اولیه، مشتریان، تخفیف‌ها، هزینه‌ها، قالب پیامک و تنظیمات است و اطلاعات محرمانه پیامک را حذف می‌کند.
- پس از ورود، رابط داده‌های موجود را از MySQL bootstrap می‌کند؛ تاریخچه سفارش‌های قبلی هنوز در این انتقال وارد نمی‌شود و تغییرات بعدی UI نیز هنوز به‌طور کامل در سرور ذخیره نمی‌شوند.
- سطح دسترسی منابع POS بر اساس نقش محدود شده است.
- ابطال نشست‌های کاربران پس از تغییر رمز/نقش/وضعیت حساب با `session_version` اضافه شد؛ migration سازگار برای دیتابیس‌های موجود نیز افزوده شد.
- تغییرات حساب مدیر در تراکنش با قفل سراسری انجام می‌شود تا دو درخواست هم‌زمان نتوانند آخرین مدیر فعال را حذف کنند.
- README فارسی نصب و محدودیت‌ها بازنویسی شد.
- رابط اصلی POS اکنون نشست PHP را هنگام بارگذاری بررسی می‌کند؛ ورود، راه‌اندازی مدیر اولیه، تغییر اجباری رمز و خروج از طریق API PHP انجام می‌شوند.
- انتخاب دستی نقش از رابط حذف شد و منوی عملیات از نقش کاربر نشست PHP ساخته می‌شود.
- ارسال پیامک به endpoint احراز هویت‌شده PHP منتقل شد؛ اعتبارنامه‌ها فقط از `private/config.php` خوانده می‌شوند و فیلدهای اعتبارنامه از UI حذف شده‌اند.
- مسیر قدیمی `/api/sms` حذف شد و مستندات تنظیم خصوصی پیامک به‌روز شدند.
- CI شاخه اضافه شد؛ آخرین اجرای کامل روی commit `4bdd0ad99a954efb9c6ad0542d7717ff6542a188` موفق بود: نصب وابستگی‌ها، PHP lint، TypeScript، تست‌های مستقل و ESLint.
- تست‌های قدیمی `scripts/**/*.test.mjs` به فایل‌های خصوصی `.grok/skills/og` وابستگی دارند و در runner مخزن قابل اجرا نیستند؛ CI به‌جای آن تست‌های مستقل قابل توزیع را اجرا می‌کند.

- ثبت سفارش اکنون مصرف recipe را از اطلاعات محصول در MySQL محاسبه و مواد اولیه را با قفل `FOR UPDATE` در همان تراکنش سفارش کم می‌کند؛ موجودی ناکافی باعث رد سفارش می‌شود. امتیاز مشتری، مبلغ خرید و تعداد مراجعه نیز با قفل رکورد مشتری و در همان تراکنش به‌روز می‌شود. ترتیب قفل مواد اولیه ثابت شده و retry با کلید idempotency اثرها را تکرار نمی‌کند.
- تغییر دستی موجودی مواد اولیه دیگر با بازنویسی کل رکورد انجام نمی‌شود؛ endpoint اختصاصی با `SELECT ... FOR UPDATE` مقدار جاری MySQL را قفل می‌کند، delta را اعمال می‌کند، موجودی منفی را رد می‌کند و تغییر را در audit log ثبت می‌کند. رابط انبار از همین مسیر اتمیک استفاده می‌کند؛ بنابراین افزایش/کاهش هم‌زمان از چند دستگاه روی مقدار تازه سرور جمع می‌شود.
- صندوقدار می‌تواند اطلاعات تماس مشتری را ثبت/ویرایش کند، اما API فیلدهای امتیاز، مبلغ خرید، تعداد مراجعه و زمان ایجاد را از مقدار موجود در MySQL حفظ می‌کند؛ برای مشتری جدید نیز شمارنده‌های وفاداری از صفر آغاز می‌شوند. تست HTTP این محدودیت را با payload دستکاری‌شده بررسی می‌کند.
- خروجی پشتیبان و بازیابی تنظیمات اکنون از endpointهای مدیرمحور MySQL انجام می‌شود. بازیابی فقط روی دیتابیس POS خالی و با تراکنش واحد مجاز است؛ اطلاعات حساب‌های کاربری مقصد حفظ می‌شوند، اعتبارنامه‌های پیامک صادر نمی‌شوند و روی دیتابیس پر هیچ بازنویسی انجام نمی‌شود. تست HTTP، بازیابی کامل سفارش‌ها و دفترهای تراکنشی و رد کردن دیتابیس پر را بررسی می‌کند.
- پس از هر تغییر وضعیت سفارش، رابط بلافاصله bootstrap کامل MySQL را دوباره دریافت می‌کند؛ در نتیجه اثر لغو سفارش بر موجودی، امتیاز مشتری و سهمیه کد تخفیف منتظر polling بعدی نمی‌ماند. اگر refresh موقتاً شکست بخورد، وضعیت سفارش ثبت‌شده باقی می‌ماند و polling دوره‌ای دوباره تلاش می‌کند.
- همگام‌سازی دوره‌ای چنددستگاهی در رابط اضافه شد: پس از ورود، bootstrap مرکزی هر ۱۵ ثانیه و هنگام بازگشت تب به حالت فعال/تمرکز پنجره دوباره دریافت می‌شود؛ درخواست‌ها هم‌پوشانی ندارند و خطای موقت شبکه آخرین وضعیت سالم را پاک نمی‌کند.

## هنوز انجام نشده و نباید پنهان بماند
- Zustand persist حذف شده است؛ داده‌های عملیاتی فقط در حافظه مرورگر نگه‌داری می‌شوند و bootstrap سرور snapshot هر نقش را جایگزین می‌کند. داده قدیمی `grillcash-v1` فقط از مسیر انتقال صریح به دیتابیس خالی خوانده و پس از انتقال موفق حذف می‌شود. همگام‌سازی همچنان polling هر ۱۵ ثانیه است، نه بلادرنگ.
- انتقال تاریخچه سفارش‌های قدیمی به MySQL؛ ابزار import legacy فقط داده‌های اصلی غیرسفارشی را وارد می‌کند.
- پوشش همه عملیات ویرایش/حذف UI با MySQL هنوز کامل نیست؛ مسیرهای اصلی CRUD منو، موجودی، مشتری، تخفیف، هزینه، قالب و تنظیمات وصل شده‌اند، اما مدیریت کامل همه فیلدها و عملیات‌های فرعی و همگام‌سازی بین دستگاه‌ها باقی است.
- آزمون فشار هم‌زمانی و صحت تراکنش‌ها روی MySQL واقعی هنوز انجام نشده است؛ منطق تراکنشی در کد پیاده شده اما CI جایگزین MySQL staging نیست.
- اعتبارسنجی کامل ارسال SMS روی هاست، گزارش‌ها، بکاپ/بازیابی و تست چند دستگاه.
- مسیر فعال cPanel یک SPA مستقل با Vite + React + TanStack Router است؛ `src/main.tsx` و `index.html` ورودی آن هستند. shell مخصوص TanStack Start از `src/routes/__root.tsx` حذف شده و routeTree به مسیرهای واقعی `src/routes` محدود شده است.
- `npm run build:cpanel` علاوه بر build استاتیک، `dist-cpanel/` را با frontend، PHP API، نمونه تنظیمات خصوصی، schema و migrationها و راهنمای نصب تولید و اعتبارسنجی می‌کند. CI کامل روی commit `d3632e38036d6002a6c38f713018ca367d69d8db` موفق شد و artifact با نام `3food-pos-cpanel` در run `44098838943` بارگذاری شد.
- `.htaccess` اکنون API PHP را پیش از fallback محافظت‌شده SPA بررسی می‌کند؛ تست رگرسیون این ترتیب در `scripts/cpanel-htaccess.test.mjs` اضافه شده است. این تست جایگزین build مرورگر یا آزمون Apache واقعی نیست.
- build استاتیک، package validation و artifact upload در CI روی commit `d3632e3` همگی موفق شده‌اند؛ تست واقعی روی cPanel هنوز انجام نشده است.
- اتصال واقعی MySQL/PDO_MYSQL و ارسال پیامک واقعی؛ نیازمند تنظیمات خصوصی cPanel و آزمایش روی staging است.

## نتیجه
این شاخه یک نسخه توسعه‌ای با API PHP/MySQL و اتصال بخشی از عملیات POS است، نه محصول نهایی آماده نصب در صندوق. تا تولید build استاتیک، تکمیل همگام‌سازی UI، آزمون MySQL واقعی و end-to-end روی staging و بررسی backup/restore انجام نشده، منتشر نشود.


## ادامه تکمیل نسخه قابل نصب — 2026-11-22

- گزارش‌های محصولات پرفروش و روش پرداخت در رابط گزارش‌گیری از تجمیع کامل PHP/MySQL استفاده می‌کنند؛ دیگر این دو نمودار به فهرست محدود سفارش‌های بارگذاری‌شده در حافظه مرورگر متکی نیستند.
- گزارش انبار، مصرف هر ماده اولیه را از دفتر اثرهای سفارش در بازه انتخابی محاسبه و در صفحه گزارش و خروجی Excel نمایش می‌دهد؛ اثرهای برگشت‌خورده و سفارش‌های لغوشده در مصرف خالص لحاظ نمی‌شوند.
- جمع هزینه‌ها بر اساس دسته در صفحه گزارش نیز از تجمیع سرور و بازه تاریخ انتخابی خوانده می‌شود؛ دیگر به snapshot محلی مرورگر متکی نیست. پس از افزودن، ویرایش یا حذف هزینه نیز گزارش زنده بلافاصله از سرور تازه‌سازی می‌شود.
- ویرایش نام دسته هزینه در تراکنش سرور، دسته هزینه‌های ثبت‌شده را نیز به نام جدید منتقل می‌کند؛ حذف دسته دارای سابقه مالی در API مسدود است. صفحه مستقل مدیریت هزینه‌ها نیز کنترل‌های ویرایش/حذف دسته را نمایش می‌دهد. نام دسته‌ها در سمت سرور نیز یکتا نگه داشته می‌شود. اعتبارسنجی طول نام نیز بر اساس تعداد نویسه‌های واقعی Unicode انجام می‌شود، نه تعداد بایت UTF-8.
- اگر دریافت گزارش مرکزی شکست بخورد، صفحه دیگر آمار ناقص cache مرورگر را به‌عنوان گزارش مالی معتبر نمایش نمی‌دهد؛ خروجی Excel و چاپ تا دریافت گزارش سرور غیرفعال می‌مانند.
- در نصب تازه، اگر هنوز هیچ دسته هزینه‌ای ثبت نشده باشد، دسته‌های پایه موردنیاز به‌صورت خودکار و با شناسه‌های ثابت در MySQL ایجاد می‌شوند. داده‌های دسته‌بندی موجود بازنویسی نمی‌شوند.
- اسکریپت بسته‌بندی cPanel علاوه بر پوشه `dist-cpanel/` آرشیو مستقل `3food-pos-cpanel.zip` می‌سازد. آرشیو فقط خروجی عمومی، نمونه تنظیمات خصوصی و schema/migrationهای V2 را در بر می‌گیرد؛ تنظیم خصوصی واقعی در بسته قرار نمی‌گیرد.
- GitHub Actions برای ZIP جداگانه artifact بارگذاری می‌کند تا بسته مستقیماً دریافت‌پذیر باشد.
- آستانه هشدار تأخیر سفارش در تنظیمات مدیر قابل تعیین است (۱ تا ۲۴۰ دقیقه، پیش‌فرض ۲۰ دقیقه) و سفارش‌های جدید/در حال آماده‌سازی پس از عبور از آن در فهرست سفارش‌ها علامت‌گذاری می‌شوند. زمان سپری‌شده همچنان از timestamp ثبت‌شده در سرور محاسبه می‌شود.

- دفتر تأمین‌کنندگان ایمن‌تر شد: ثبت/حذف مستقیم رکوردهای دفتر خرید و تسویه از CRUD عمومی مسدود است؛ مانده تأمین‌کننده در ویرایش مشخصات فقط از مقدار سرور حفظ می‌شود و حذف تأمین‌کننده دارای سابقه مالی رد می‌شود. ثبت خرید/پرداخت همچنان فقط از endpoint تراکنشی و اتمیک انجام می‌شود.
- اعتبارسنجی مالی تراکنش تأمین‌کننده سخت‌گیرانه‌تر شد: مبلغ خرید/پرداخت و قیمت واحد باید تومان صحیح باشند؛ مقدار ماده اولیه باید مثبت، محدود و حداکثر سه رقم اعشار باشد. ورودی‌های اعشاری/غیرمتناهی/بیش‌ازحد قبل از تغییر موجودی یا بدهی رد می‌شوند.
- تسویه بدهی تأمین‌کننده غیرفعال مجاز باقی می‌ماند؛ غیرفعال‌سازی فقط ثبت خرید جدید را مسدود می‌کند و مانع پرداخت بدهی‌های قبلی نمی‌شود.
- در ویرایش عمومی مواد اولیه، موجودی و بهای واحد ثبت‌شده در سرور حفظ می‌شود؛ تغییر موجودی فقط از endpoint تعدیل دارای قفل تراکنشی و audit و تغییر بهای واحد از مسیر خرید تأمین‌کننده انجام می‌شود. صفحه انبار امکان افزایش یا کاهش دستی با مقدار اعشاری تا سه رقم را نیز دارد و تغییر فقط پس از تأیید سرور در رابط اعمال می‌شود. ایجاد ماده اولیه جدید نیز در سمت سرور با موجودی و ارزش صفر شروع می‌شود و مقادیر ارسالی کلاینت نمی‌توانند موجودی اولیه جعلی ثبت کنند. حذف ماده اولیه‌ای که در دستور ساخت محصولات، خریدهای ثبت‌شده یا اثرهای مصرف سفارش استفاده شده باشد نیز در API رد می‌شود تا گزارش و تاریخچه انبار خراب نشود.
