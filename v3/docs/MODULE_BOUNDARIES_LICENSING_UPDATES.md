# مرزبندی لایسنس، قابلیت‌های تجاری و مدیریت مرکزی — V3

## وضعیت فعلی و تصمیم محصول
محصول با هویت ثابت PersiaCoder.ir عرضه می‌شود؛ White-Label در محدوده نیست. مدل تجاری مصوب، لایسنس دائمی همراه یک سال به‌روزرسانی است. پلن‌ها و محدودیت‌های قابلیت باید از پنل مرکزی قابل تنظیم باشند. نصب مشتری می‌تواند روی هاست اختصاصی یا زیرساخت مدیریت‌شده باشد و اعتبار آفلاین نیز باید از مرکز قابل پیکربندی باشد. در عین حال عملیات روزمره نصب مستقل نباید وابستگی دائمی به مرکز داشته باشد.

در ساختار فعلی V3، اسناد قابلیت‌ها و ERD تجاری وجود دارند، اما در فهرست فایل‌های Backend فعلی سرویس/کنترلر اجرایی License، Entitlement، Central Admin یا Update Management دیده نمی‌شود. این موارد را نباید پیاده‌سازی‌شده تلقی کرد.

## تفکیک دامنه‌ها
- **Installation Identity:** شناسه یکتای نصب، کلید عمومی/خصوصی یا credential نصب، اثرانگشت حداقلی و وضعیت ثبت.
- **License:** سند امضاشده شامل شناسه نصب/مشتری، نوع مجوز، تاریخ صدور، دامنه نسخه، قابلیت‌های پایه، دوره به‌روزرسانی و سیاست grace/offline.
- **Entitlement Resolver:** تبدیل license + plan + overrides + local business settings به تصمیم قابلیت؛ این تصمیم باید یکسان در UI و Backend باشد، اما enforcement نهایی همیشه Backend است.
- **Central Admin:** مدیریت مشتری، نصب‌ها، صدور/تمدید/ابطال مجوز، تعریف پلن و feature flags، محدودیت‌ها، نسخه‌های منتشرشده و رخدادهای پشتیبانی.
- **Update Manager:** کانال انتشار، manifest امضاشده، سازگاری نسخه، پیش‌نیاز migration، checksum بسته، rollout و rollback policy.
- **Local Runtime:** اعتبارسنجی امضای مجوز، cache امن، آخرین وضعیت معتبر، grace period و اجرای عملیات مجاز در قطعی ارتباط.
- **Audit & Support:** ثبت صدور/ابطال/تغییر پلن/انتشار؛ بدون ذخیره secret یا داده غیرضروری مشتری.

## اصول امنیت و قابلیت اطمینان
1. نصب فقط کلید عمومی صادرکننده را برای اعتبارسنجی license و update manifest لازم دارد؛ secret امضای مرکزی هرگز داخل بسته مشتری قرار نگیرد.
2. مجوز و manifest با امضای دیجیتال قابل‌اعتبارسنجی باشند؛ اتکا به پاسخ JSON بدون امضا کافی نیست.
3. اعتبارسنجی تاریخ با clock rollback و تغییر ساعت سیستم مقابله کند؛ سیاست باید مستند و قابل پشتیبانی باشد.
4. در قطعی مرکز، آخرین license معتبر تا مدت offline قابل‌پیکربندی قابل استفاده است؛ انقضای grace باید رفتار روشن و غیرمخرب داشته باشد.
5. قطع ارتباط با مرکز نباید داده مشتری را قفل، حذف یا خراب کند؛ فقط قابلیت‌هایی که واقعاً نیازمند entitlement هستند محدود شوند.
6. UI صرفاً نمایش وضعیت است؛ هر endpoint حساس باید entitlement را در Backend بررسی کند.
7. تغییر پلن و کاهش سقف نباید داده موجود را حذف کند؛ کاهش سقف زیر مصرف فعلی باید به حالت نیازمند اقدام مدیر برود.
8. نصب مشتری فقط بسته به‌روزرسانی امضاشده و سازگار را نصب کند؛ backup و preflight قبل از migration الزامی است.
9. update ناموفق باید به نسخه قبلی یا recovery مستند برسد؛ migration مخرب بدون مسیر بازیابی مجاز نیست.
10. شناسه نصب و داده‌های telemetry حداقلی باشند؛ داده عملیاتی مشتری بدون نیاز و رضایت به مرکز ارسال نشود.

## مدل entitlement پیشنهادی
تصمیم قابلیت به‌صورت ترکیب این ورودی‌ها محاسبه شود:
- قابلیت‌های ذاتی نسخه/محصول؛
- پلن فعال و overrideهای مشتری در پنل مرکزی؛
- اعتبار و دامنه مجوز نصب؛
- تنظیمات محلی مدیر کسب‌وکار؛
- وابستگی‌های ماژول و محدودیت‌های منابع.

قواعد precedence باید صریح باشند: مجوز مرکزی می‌تواند قابلیت تجاری را مجاز کند یا محدودیت سقف تعیین کند؛ مدیر محلی فقط در همان محدوده مجاز، قابلیت‌های عملیاتی را روشن/خاموش کند. هیچ تنظیم UI نباید محدودیت امنیتی یا entitlement سرور را دور بزند.

## قرارداد Update Manifest
حداقل فیلدهای منطقی:
- product_id و release_id؛
- version و minimum_supported_version؛
- channel و published_at؛
- package checksum و signature؛
- حداقل نسخه PHP/DB و پیش‌نیازهای محیط؛
- فهرست migrationها و برچسب backward compatibility؛
- backup_required، maintenance_mode و recovery instructions.

Manifest باید نسخه‌بندی شود و parser نسخه قدیمی رفتار fail-closed امن داشته باشد. فایل بسته نباید از URL دلخواه کاربر نصب شود.

## مراحل اجرایی
1. تعیین مدل داده installation/license/plan/feature و قراردادهای امضا.
2. ساخت Local License Verifier و Entitlement Resolver مستقل از HTTP.
3. افزودن middleware/policy برای enforce قابلیت‌ها و سقف‌ها در Backend.
4. طراحی API پنل مرکزی و ثبت audit برای عملیات تجاری.
5. ساخت manifest امضاشده و Update Client با preflight، backup و migration runner.
6. افزودن وضعیت قابل فهم در UI، هشدار انقضا و grace، و گزارش پشتیبانی.
7. تست سناریوهای offline، clock rollback، license tamper، revoke، کاهش سقف، update خراب و rollback.

## معیار پذیرش
- مجوز دستکاری‌شده یا متعلق به نصب دیگر رد شود.
- نصب در محدوده offline معتبر بدون اتصال دائمی به مرکز کار کند.
- محدودیت entitlement با API مستقیم قابل دور زدن نباشد.
- تغییر پلن/ابطال/تمدید قابل ردیابی باشد.
- update فقط با manifest و بسته معتبر نصب شود.
- backup/preflight پیش از migration اجرا و مسیر بازیابی مستند باشد.
- کاهش قابلیت یا سقف داده قبلی را حذف نکند.

این سند قرارداد معماری است و به معنی وجود لایسنس، پنل مرکزی یا updater اجرایی نیست.
