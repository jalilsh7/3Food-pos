# مرزبندی فروشگاه آنلاین و یکپارچگی‌ها — V3

## وضعیت واقعی فعلی
در شاخه توسعه، رابط `v3/frontend/src/features/storefront/StorefrontWorkspace.tsx` یک پیش‌نمایش تعاملی است. داده منو در آرایه ثابت قرار دارد، سبد خرید در state محلی مرورگر نگهداری می‌شود و خود صفحه صریحاً اعلام می‌کند که ثبت سفارش، هزینه ارسال، پرداخت، موجودی و ساعات کاری به Backend متصل نیستند. درخت فعلی Backend V3 نیز controller/service اختصاصی برای storefront یا connectorهای بیرونی نشان نمی‌دهد. بنابراین وجود صفحه پیش‌نمایش را نباید با فروشگاه آنلاین عملیاتی اشتباه گرفت.

## مسئولیت‌ها
- **Storefront Presentation:** نمایش برند کسب‌وکار، منو، دسته‌ها، جزئیات محصول، افزودنی‌ها، ساعات/روزهای سفارش، روش دریافت و وضعیت قابل‌فروش‌بودن.
- **Public Storefront Application:** دریافت تنظیمات عمومی مجاز، خواندن منوی منتشرشده، ساخت پیش‌نویس سفارش و ثبت سفارش مهمان/مشتری با اعتبارسنجی سمت سرور.
- **Order Core:** مرجع نهایی قیمت و تخفیف، snapshot اقلام و افزودنی‌ها، وضعیت سفارش، idempotency و چرخه عمر؛ storefront نباید منطق سفارش موازی بسازد.
- **Fulfillment & Delivery:** قواعد محدوده ارسال، هزینه، حداقل سفارش، زمان آماده‌سازی، ظرفیت و روش دریافت؛ محاسبات نهایی سمت Backend.
- **Payment Integration:** پرداخت آنلاین فقط برای سفارش وب؛ ایجاد intent/درخواست، callback امن، استعلام نتیجه از درگاه، ثبت ledger و جلوگیری از callback تکراری. پرداخت حضوری صندوق در این مسیر ادغام نشود.
- **Integration Adapters:** WooCommerce و سایر سرویس‌ها از طریق adapterهای مستقل؛ کلید و secret فقط در Backend.
- **Sync & Reconciliation:** صف، retry با backoff، idempotency، cursor/watermark، ثبت خطا و تطبیق دوره‌ای؛ شکست اتصال خارجی نباید داده عملیاتی POS را بی‌ردپا تغییر دهد.

## قواعد اتصال WooCommerce
1. انتخاب منبع مرجع محصول و موجودی باید مستقل و صریح باشد: POS یا WooCommerce؛ دو منبع هم‌زمان برای یک داده مرجع مجاز نیستند.
2. نگاشت محصول/variation با شناسه خارجی پایدار و شناسه داخلی انجام شود؛ عنوان یا SKU به‌تنهایی کلید قطعی نیست.
3. سفارش واردشده شناسه خارجی، کانال، snapshot و زمان دریافت دارد؛ webhook تکراری نباید سفارش دوم بسازد.
4. تغییر وضعیت فقط برای وضعیت‌های نگاشت‌شده و مجاز ارسال شود؛ حلقه sync با origin marker و version/updated-at کنترل شود.
5. تعارض موجودی و overselling باید با سیاست واحد و ثبت نتیجه حل شود؛ sync دوره‌ای مکمل webhook است.
6. حذف/غیرفعال‌شدن اتصال، داده و سفارش‌های قبلی را حذف نمی‌کند؛ عملیات صف‌شده باید قابل مشاهده و تعیین تکلیف باشند.

## قراردادهای امنیتی
- endpoint عمومی فقط داده منتشرشده و فیلدهای مجاز را برگرداند؛ داده مشتریان، هزینه داخلی، یادداشت کارکنان و تنظیمات محرمانه هرگز public نیست.
- ثبت سفارش عمومی rate limit، اعتبارسنجی ورودی، محدودیت اندازه payload، ضد replay و idempotency لازم دارد.
- قیمت، تخفیف، هزینه ارسال، مالیات، موجودی و وضعیت پرداخت از کلاینت پذیرفته نمی‌شوند؛ Backend دوباره محاسبه/تأیید می‌کند.
- callback درگاه باید امضا/توکن را اعتبارسنجی کند و در صورت نیاز نتیجه را server-to-server استعلام کند.
- کلیدهای WooCommerce و درگاه رمزگذاری‌شده و خارج از frontend/log نگهداری شوند.
- اطلاعات شخصی سفارش مهمان حداقلی، scoped و دارای سیاست retention باشد.

## ترتیب پیاده‌سازی
1. استخراج قراردادهای DTO و public read model برای storefront بدون اتصال مستقیم UI به schema.
2. افزودن backend read endpoints برای storefront profile/menu/availability.
3. ثبت سفارش وب از مسیر Order Application موجود با idempotency و snapshot؛ عدم ساخت مدل سفارش دوم.
4. افزودن fulfillment policy و سپس درگاه آنلاین به‌عنوان adapter مستقل.
5. ایجاد integration registry و WooCommerce adapter، سپس webhook inbox/outbox و reconciliation.
6. نمایش وضعیت sync و خطاهای قابل اقدام در تنظیمات مدیریتی.

## معیار پذیرش
- منوی storefront از Backend خوانده شود و داده ثابت نمونه منبع عملیاتی نباشد.
- قیمت و موجودی نهایی سمت سرور کنترل شوند.
- سفارش آنلاین در همان چرخه عمر و گزارش سفارش POS دیده شود.
- callback و webhook تکراری اثر تکراری نسازند.
- قطع سرویس خارجی باعث از دست رفتن سفارش محلی یا پرداخت تأییدشده نشود.
- منبع مرجع محصول/موجودی قابل مشاهده و تغییر آن کنترل‌شده باشد.
- secrets در bundle، پاسخ عمومی یا log ظاهر نشوند.

این سند مرزبندی و مسیر refactor را تعریف می‌کند؛ پیاده‌سازی و تست این قابلیت‌ها هنوز جداگانه لازم است.
