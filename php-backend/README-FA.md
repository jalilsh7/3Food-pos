# 3Food POS — PHP/MySQL backend migration (مرحله توسعه)

این بسته شامل زیرساخت PHP برای جایگزینی تدریجی سرویس Node.js و ذخیره‌سازی مرکزی MySQL است. **این بسته هنوز نسخه نهایی قابل استفاده در فروشگاه نیست**؛ ورود و ارسال پیامک React به APIهای PHP وصل شده‌اند، اما همگام‌سازی کامل داده‌های POS، منطق تجاری سفارش، انتشار استاتیک و آزمون نهایی هاست هنوز باقی است.

## نیازمندی‌ها
- PHP 8.2+ (حداقل کد PHP 8.1)
- افزونه‌های `PDO` و `pdo_mysql`
- MySQL 5.7.8+ یا MariaDB سازگار با JSON و InnoDB
- Apache با `mod_rewrite` و پشتیبانی `.htaccess`
- SSL فعال

## ساختار و نصب آزمایشی
1. در cPanel دیتابیس MySQL و کاربر اختصاصی بسازید و دسترسی کامل را فقط به همان دیتابیس بدهید.
2. `schema.sql` را در phpMyAdmin وارد کنید. اگر دیتابیس را قبلاً با نسخه قدیمی‌تر ساخته‌اید، فایل‌های `migrations/002-session-version.sql` و `migrations/003-order-idempotency.sql`، سپس `migrations/004-order-effects-ledger.sql`، `migrations/005-order-discount-code.sql` و در پایان `migrations/006-discount-redemptions-ledger.sql` را به‌ترتیب و هرکدام فقط یک‌بار اجرا کنید.
3. `private/config.example.php` را به `private/config.php` کپی کنید و اطلاعات دیتابیس را وارد کنید.
4. برای `app_key` و `setup_token` دو مقدار تصادفی مستقل با حداقل 64 نویسه hex تولید کنید. از قرار دادن آن‌ها در پوشه عمومی یا JavaScript خودداری کنید.
5. برای پیامک، فقط در `private/config.php` مقدار `sms.provider` را `national_payamak` و مقادیر `username`، `password` و `sender` را تنظیم کنید. این اطلاعات را در تنظیمات مرورگر یا فایل‌های Git قرار ندهید.
6. Document Root زیردامنه را روی `php-backend/public` قرار دهید؛ پوشه `private` باید بیرون Document Root باشد.
7. SSL را فعال کنید.
8. `GET /api/v1/health` را بررسی کنید.
9. در صفحه ورود POS، راه‌اندازی اولیه را انجام دهید و توکن یک‌بارمصرف را وارد کنید. رمز باید حداقل 12 نویسه باشد.
10. پس از ایجاد مدیر، مقدار `setup_token` را از `private/config.php` حذف کنید.

## APIهای پیاده‌سازی‌شده
| Method | Path | دسترسی | توضیح |
|---|---|---|---|
| GET | `/api/v1/health` | عمومی | سلامت API و اتصال MySQL |
| GET | `/api/v1/setup/status` | عمومی | اعلام اینکه راه‌اندازی اولیه لازم است یا نه |
| POST | `/api/v1/setup/manager` | توکن یک‌بارمصرف | ایجاد مدیر اولیه و شروع نشست مدیر |
| POST | `/api/v1/auth/login` | عمومی | ورود با نام کاربری و رمز |
| GET | `/api/v1/auth/me` | نشست | اطلاعات نشست جاری و CSRF |
| POST | `/api/v1/auth/logout` | نشست + CSRF | خروج |
| POST | `/api/v1/auth/change-password` | نشست + CSRF | تغییر رمز |
| GET/POST | `/api/v1/users` | مدیر | فهرست و ایجاد کاربران |
| PATCH | `/api/v1/users/{id}` | مدیر + CSRF | تغییر حساب کاربر |
| POST | `/api/v1/migration/import` | مدیر + CSRF | انتقال یک‌باره داده‌های اصلی دستگاه به دیتابیس خالی (بدون تاریخچه سفارش‌ها) |
| GET | `/api/v1/bootstrap` | کاربر واردشده | دریافت داده مرکزی و سفارش‌ها |
| GET/POST/DELETE | `/api/v1/records/{resource}` | براساس نقش | داده‌های دسته، محصول، مواد، مشتری، تخفیف، هزینه، تنظیمات، قالب پیامک و لاگ پیامک |
| POST | `/api/v1/orders` | مدیر/صندوق‌دار + CSRF | ثبت سفارش با شماره ترتیبی اتمیک، کنترل قیمت و کلید idempotency برای جلوگیری از سفارش تکراری در retry |
| PATCH | `/api/v1/orders/{id}/status` | مدیر/آشپز + CSRF | تغییر وضعیت سفارش |
| POST | `/api/v1/sms/send` | مدیر/صندوق‌دار + CSRF | ارسال پیامک با اعتبارنامه خصوصی سرور |

نقش‌ها: `manager`, `cashier`, `kitchen`.

## نکات مهم و محدودیت‌های باقی‌مانده
- صفحه اصلی React اکنون ورود، راه‌اندازی اولیه مدیر، تغییر اجباری رمز و خروج را با نشست PHP انجام می‌دهد؛ انتخاب دستی نقش از رابط حذف شده است.
- پس از ورود، رابط برای همگام‌سازی چنددستگاهی هر ۱۵ ثانیه bootstrap را دوباره می‌خواند و هنگام بازگشت پنجره/تب به حالت فعال نیز فوراً تازه‌سازی می‌کند. درخواست‌های هم‌زمان جلوگیری می‌شوند؛ خطای گذرای شبکه داده سالم فعلی را پاک نمی‌کند.
- در صفحه تنظیمات، مدیر می‌تواند داده‌های اصلی دستگاه را یک‌بار به دیتابیس خالی منتقل کند؛ این انتقال شامل دسته‌ها، محصولات، مواد اولیه، مشتریان، تخفیف‌ها، هزینه‌ها، قالب‌ها و تنظیمات است، اما تاریخچه سفارش‌ها را منتقل نمی‌کند. پس از آن داده‌های موجود از bootstrap سرور بارگذاری می‌شوند؛ همگام‌سازی خودکار همه ویرایش‌های بعدی UI هنوز تکمیل نشده است.
- مالیات از تنظیمات مرکزی فروشگاه قابل فعال/غیرفعال‌کردن است؛ در حالت غیرفعال، مالیات سفارش صفر محاسبه می‌شود. در حالت فعال، درصد تنظیم‌شده (۰ تا ۱۰۰) روی مبلغ پس از تخفیف‌ها اعمال می‌شود. API مقدار مالیات و مبلغ نهایی را با تنظیمات MySQL دوباره محاسبه و اعتبارسنجی می‌کند و به مبلغ مالیات ارسالی مرورگر اعتماد نمی‌کند. اقلام سفارش در PHP از روی محصولات و گزینه‌های ثبت‌شده در MySQL بازسازی می‌شوند؛ نام محصول، برچسب گزینه و قیمت ذخیره‌شده از مرورگر پذیرفته نمی‌شود. رکورد محصولات تا پایان تراکنش قفل و تغییر هم‌زمان قیمت/دستور ساخت باعث رد سفارش و نیاز به محاسبه مجدد می‌شود. مقدار و شناسه گزینه‌ها نیز کنترل و گزینه تکراری رد می‌شود.

کد تخفیف در PHP با داده مرکزی MySQL اعتبارسنجی می‌شود: بازه تاریخ، حداقل مبلغ، درصد/مبلغ ثابت، سقف تخفیف درصدی، سقف مصرف کلی، سطح عضویت و محدودیت هر مشتری. ثبت مصرف کد و سفارش در یک تراکنش و با قفل رکورد تخفیف انجام می‌شود؛ شمارش سهمیه از جدول تغییرناپذیر `pos_discount_redemptions` انجام می‌شود تا ویرایش دستی شمارنده نتواند محدودیت را دور بزند. کد مصرف‌شده در سفارش ذخیره می‌شود و با لغو سفارش، سهمیه آن نیز در همان تراکنش آزاد می‌شود. موجودی امتیاز مشتری اکنون هنگام ثبت سفارش در تراکنش و با قفل رکورد بررسی و به‌روز می‌شود.
- برای ثبت سفارش از `idempotencyKey` یکتای UUID استفاده کنید و هنگام retry همان کلید را دوباره بفرستید؛ استفاده دوباره از همان کلید با payload متفاوت با خطای 409 رد می‌شود.
- هنگام ثبت سفارش، مصرف مواد اولیه از recipe ذخیره‌شده سمت سرور محاسبه می‌شود؛ ردیف‌های انبار با `SELECT ... FOR UPDATE` قفل و کسر موجودی در همان تراکنش سفارش انجام می‌شود. سفارش در صورت ناکافی بودن موجودی یا نبودن ماده اولیه رد می‌شود. تغییر موجودی مشتری (کسر امتیاز، افزودن امتیاز، افزایش مبلغ خرید و تعداد مراجعه) نیز با قفل رکورد مشتری و در همان تراکنش انجام می‌شود؛ retry با idempotency key اثرها را دوباره اعمال نمی‌کند. اثرهای هر سفارش در جدول `pos_order_effects` ثبت می‌شوند. با لغو سفارش، موجودی مواد و اثر امتیاز/مبلغ خرید/تعداد مراجعه در همان تراکنش بازگردانده و اثرها یک‌بار علامت‌گذاری می‌شوند؛ درخواست لغو تکراری نمی‌تواند بازگشت را دوباره اعمال کند. اگر امتیاز کسب‌شده سفارش قبلاً خرج شده باشد، لغو با خطای 409 متوقف می‌شود تا موجودی امتیاز منفی یا ناسازگار نشود. سفارش‌های قدیمی که پیش از نصب ledger ثبت شده‌اند اثر قابل‌بازگشتی ندارند. آزمون هم‌زمانی روی MySQL واقعی، گزارش‌ها، بکاپ/بازیابی و همگام‌سازی بلادرنگ هنوز کامل نیستند.
- ارسال پیامک از مسیر PHP انجام می‌شود و اعتبارنامه از `private/config.php` خوانده می‌شود؛ رابط مرورگر فقط شماره، متن و شناسه الگو را می‌فرستد. فعال‌سازی واقعی نیازمند تنظیم اعتبارنامه و آزمایش ارسال در هاست است.
- فونت و assets خارجی و حذف نهایی Grok/Vercel از مسیر انتشار هنوز نیازمند تکمیل است.
- تغییرات اخیر در CI با PHP lint، TypeScript، تست‌های مستقل و ESLint بررسی می‌شوند؛ build استاتیک و آزمون end-to-end روی هاست هنوز باقی است. اتصال واقعی MySQL و ارسال پیامک نیز تا تنظیم cPanel تأییدشدنی نیست.

## بررسی نحوی
```bash
php -l public/api/index.php
```

**هشدار:** این بسته برای ادامه توسعه و تست staging است؛ آن را جایگزین نسخه عملیاتی صندوق نکنید.
